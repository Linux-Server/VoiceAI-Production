# Gemma 4 load, capacity and startup results — 2026-10-13

Endpoint: `gemma4-serve-eu` v5 (vLLM v0.31.0, `gemma-4-26b-a4b-w4a16`, eu-west), measured from the client machine.
Every container today ran on an **A100-40GB** (bf16 KV cache). v5 has request/output logging on (`LOG_REQUESTS = True`).

## Short prompts under load

`load_test.py`: short prompt, exactly 128 output tokens (`ignore_eos`), a new connection per request (connect time not
counted in TTFT). Started on one warm container; `target_concurrency` is 32.

| Callers | Requests | Errors | Client TTFT p50 / p90 | ITL p50 / p90 | End to end p50 / p90 | Tokens/s per caller | Total tokens/s |
|---|---|---|---|---|---|---|---|
| 1 | 20 | 0 | 241 / 257 ms | 6.1 / 6.3 ms | 1,020 / 1,035 ms | 160 | 120 |
| 8 | 24 | 0 | 355 / 397 ms | 8.5 / 8.9 ms | 1,447 / 1,478 ms | 117 | 711 |
| 16 | 47 | 1 *(1)* | 378 / 430 ms | 10.6 / 11.3 ms | 1,758 / 1,797 ms | 96 | 1,205 |
| 32 | 96 | 0 | 452 / 719 ms | 13.7 / 16.1 ms | 2,291 / 2,532 ms | 77 | 1,880 |
| 48 | 144 | 0 | 478 / **2,343** ms | 16.2 / 18.3 ms | 2,608 / 4,220 ms | 69 | 2,464 |

*(1)* No 4xx/5xx or error in the server logs, so it failed between client and Modal (network); the script doesn't record the message.

- One container handles 32 short-prompt callers with p90 TTFT under 0.75 s.
- At 48, Modal started a second container (restored from snapshot, ready in 30 s); the p90 TTFT of 2.3 s is callers
  queueing on the first container while it booted.
- Request/output logging had no measurable cost: ITL matches 2026-10-12 without logging (6.1 vs 6.2 ms at 1 caller,
  8.5 vs 9.6 ms at 8).

Reproduce: `uv run python llm/load_test.py --levels 1,8,16,32,48`

## 10k-token prompt, 150 output tokens

`server_latency.py --prompt-tokens 10000 --max-tokens 150 --turns 5`: unique prompt per request (no prefix-cache hits).

| Callers | Client TTFT p50 | Server TTFT | Prefill | Queue | Server ITL |
|---|---|---|---|---|---|
| 1 | 1,188 ms | 293 ms | 108 ms | 107 ms | 13.2 ms |
| 8 | 1,947 ms | 378 ms | 179 ms | 122 ms | 13.2 ms |
| 16 | **3,472 ms** | 3,304 ms | 1,378 ms | 1,322 ms | **64.4 ms** |
| 32 | **3,650 ms** | 3,838 ms | 1,198 ms | 2,490 ms | **71.5 ms** |

**Caveat:** two containers were still up from the previous run, and Modal split requests about evenly between them (65 and
64 in the captured logs), so "32 callers" was ~16 per GPU and "16 callers" ~8 per GPU. A single GPU at 32 would be worse.
Server columns come from `/metrics` of whichever container answered the scrape, so treat them as approximate; client
TTFT is reliable.

- The limit is prefill compute, not KV memory: requests queued while fewer than 20 ran per container, and KV cache usage
  peaked at 36%. Each 10k prefill costs about 1 s of A100 time, and concurrent prefills also slow decoding (ITL 13 → 65-70 ms).
- For 10k-token traffic, plan on about 8 concurrent callers per A100 for sub-2 s TTFT. Lowering `target_concurrency`
  toward 8 would make Modal scale out sooner. Prefix caching helps most in real calls: on 2026-10-12, 10k-token
  conversations with cache hits had a 359 ms server TTFT at 8 callers.

Reproduce: `uv run python llm/server_latency.py --prompt-tokens 10000 --max-tokens 150 --concurrency 1,8,16,32 --turns 5`

## Startup after the v5 deploy

Changing the `vllm serve` command invalidates the GPU snapshot, so the first v5 container did a full boot and created a
new snapshot: ~9.5 min from container start (~11 min including deploy and GPU scheduling). The v4 container kept serving
until v5 was ready.

| Step | Time |
|---|---|
| Container start, imports, engine setup | ~2 min |
| Load weights (14.8 GiB) | 36 s |
| torch.compile (31.5 s Dynamo + 87 s graph compile) | 2 min 15 s |
| CUDA graph capture, profiling, server start | ~50 s |
| Warm-up and `/sleep` | ~20 s |
| Modal creates the GPU memory snapshot | ~3 min |
| Restore from snapshot and wake | 20 s |

Later cold starts restored the snapshot in about 30 s. v5 has no L40S snapshot yet, so its first L40S boot will be slow too.

## Empty replies (user report)

70 probe requests on a warm container (plain chat, short turns, tools offered, tool call, reply after a tool result;
streaming and not) all returned text or a tool call. Empty `content` reproduced only with thinking on and a small budget:
`enable_thinking: true` with `max_tokens` 60 or 200 returned empty `content` 4/4 times (`finish_reason=length`, the text
went to `reasoning_content`). A tool call also returns empty `content` (the reply is in `tool_calls`).
