with `server_latency.py`. Server columns come from vLLM's `/metrics` (no network). Client TTFT is the median over 20 turns per caller.
Every turn generates exactly `max_tokens` (`ignore_eos`) and has a unique prefix (no prefix-cache hits).

## Notes
- Client TTFT is 0.2–1.5 s above server TTFT, and the gap grows with prompt size and concurrency: network/proxy overhead, not the model.
- Runs were much slower end to end than the requests account for (2k run: ~5 min; 10k run: 7.5 min), consistent with that.
- The 10k run started cold: the server took 51 s to be ready (scaled to zero after 20 idle minutes).

Reproduce: `uv run python llm/server_latency.py --prompt-tokens 10000 --max-tokens 200`

The running container was an A100-40GB (bf16 KV cache).

## Speculative decoding (Gemma 4 MTP drafter, W4A16, 4 speculative tokens)

`gemma4-serve-eu` (no speculation) vs `gemma4-serve-eu-spec` (`SPEC_DECODE=1`), both on A100-40GB, measured back to back.
2k-token prompt, exactly 150 output tokens. Generation speed = time from first to last streamed token ÷ tokens.

| Callers | Server | Time per output token | Tokens/s per caller | Full turn p50 |
|---|---|---|---|---|
| 1 | no speculation | 6.61 ms | 151 | 2,230 ms |
| 1 | **speculative** | **4.10 ms** | **244** | **1,301 ms** |
| 8 | no speculation | **12.71 ms** | **79** | **3,271 ms** |
| 8 | speculative | 14.45 ms | 69 | 4,389 ms |

- One caller: generation is **1.6× faster**. At 8 callers it is **~14% slower**, and the full turn ~34% slower.
- Server counters: 54% of draft tokens accepted (18,950 of 34,988), ~3.2 tokens per target step. Offline greedy
  test on 3 prompts: 59.2%, 3.37 tokens per step, per-position 85% / 66% / 50% / 37%.
- vLLM's `inter_token_latency` metric counts per engine *step*, not per token, so with speculation it reads
  ~19.7 ms (1 caller) and is not comparable; use the end-to-end numbers above.
- Under 8 callers the speculative server's prefill was also slower (626 ms vs 141 ms server-side mean).
- Client TTFT in this run used a new connection per request, so it includes the TLS handshake and is noisy.

### 10k-token prompt, 200 output tokens (same method, both on A100-40GB)

| Callers | Server | Requests OK | Time per output token | Tokens/s per caller | Full turn p50 | Client TTFT p50 |
|---|---|---|---|---|---|---|
| 1 | no speculation | 9 / 10 | 7.73 ms | 129 | 5,359 ms | 4,075 ms |
| 1 | **speculative** | 10 / 10 | **5.45 ms** | **184** | **3,291 ms** | 2,035 ms |
| 8 | no speculation | 32 / 32 | 18.40 ms | 54 | 7,918 ms | 4,140 ms |
| 8 | **speculative** | 32 / 32 | **16.57 ms** | **60** | **7,600 ms** | 3,607 ms |

- One caller: generation **1.42× faster** (vs 1.6× at 2k). At 8 callers speculation is now **~10% faster**, where at
  2k it was ~14% slower: with long contexts each step is dominated by reading the KV cache, which speculation
  shares across several tokens.
- Client TTFT was 2-4 s here (the network to eu-west was unstable: one `Connection reset by peer`), so TTFT and
  full-turn differences are mostly network noise. Compare on time per output token.
